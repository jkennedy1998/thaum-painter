# encapsulation plan — workers/session-relay (relay transport: server + client lane)

linked project plan: `plans/project-thaum-painter-relay-transport-plan.md` (phase-2)

## pre-implementation-note
Settled truths (J 2026-09-08): real TLS via a jartanddesign.com subdomain on JOBO (certbot-managed cert/key files; the binary never does ACME itself). Raw TLS + length-prefixed NDJSON inside (no WebSocket). Invite code = one short field `<room6>-<token10>` (17 chars, no ambiguous glyphs, no prefix). Relay keeps ZERO state on disk and never interprets records — rooms die with their last member; the host owns all document truth.

The host core (`SessionHost`) and client core (`SessionClient`) are transport-agnostic and stay untouched: the relay is a second transport around them, exactly like `session-host/tcp.rs` is the first.

## intent
One boundary owns everything swappable about "how two machines find each other over the internet": the relay wire protocol, the room-routing server binary, and the client-side lane both session ends dial out through.

## core design
1. **Roles, not peer meshes.** A room has exactly one host connection and up to `MAX_ROOM_MEMBERS` joiner connections. Routing is fixed and dumb: joiner → host (every line), host → one named joiner or all (its choice). No peer-to-peer, no discovery, no presence logic — presence rides the existing `HostMessage`/`ClientMessage` channel like it does on LAN.
2. **Opaque lines.** The relay never parses session content. A frame is `{"to":"<user_id|all>","line":"<session json>"}` (host→joiner) or `{"line":"<session json>"}` (joiner→host). The inner line is the existing `ClientMessage`/`HostMessage` JSON, passed through verbatim — same bytes as the LAN wire, so the cores can't tell the difference.
3. **Hello = role claim.** First message on a connection: `{"type":"host","room":...,"token":...}` (creates/claims the room; a second host is denied `room-taken`) or `{"type":"join","room":...,"token":...,"user":"<session user id>"}` (denied: `bad-token`, `no-room`, `user-id-in-use`, `room-full`). Server replies `{"type":"ok","room":...}` or `{"type":"error","reason":...}` then closes.
4. **Codes.** `<room6>-<token10>`, Crockford-base32 alphabet minus ambiguous glyphs. Room id + room token are minted by the relay from 60 bits of OS entropy; the code IS the auth (knowing it = the invite). Codes are generated by the relay at host-claim time and returned in the `ok` frame, so the host app just displays what it got.
5. **Caps from day one** (internet-exposed from day one): max frame bytes (1 MiB default), members per room (8), rooms per server (config, default 256), join rate per connection (simple sliding window, 30 joins/min). Every cap violation = error frame + close. No persistence: rooms are in-memory only and die with the host connection (`{"type":"room-closed"}` to members).
6. **TLS at the edge, plain at the core.** The server loop is generic over `Read + Write`. Plain TCP for loopback/tests now; `rustls` with cert/key file paths for the real listener (deploy phase wires certbot output). The client lane takes a URL and does TLS always (certificate verification standard — no TOFU needed now that a real domain backs it).
7. **Reconnect story unchanged.** A dropped relay link looks exactly like a dropped LAN link to the session ends: EOF → client auto-rejoin (fresh snapshot + replay) → `take_rejoined` guards republish. The relay lane must make reconnects cheap: re-dial with the same code.

## interface delta
- `relay_codes`: `generate_code() -> (room, token, code)`, `parse_code(&str) -> Option<(room, token)>`
- `relay_protocol`: frame types (host/join/ok/error/room-closed/to+line/line), length-prefix codec with the frame cap enforced at read
- `relay_server`: `RelayCaps { max_frame_bytes, max_members, max_rooms, join_rate }`, `serve_relay(listener, caps) -> RelayServer` — generic over streams; plain TCP now, TLS listener at deploy
- `relay_client` (phase within this plan): `RelayLink::connect(url, code, role, user)` — the line-send/recv lane shape `session-host/tcp.rs` wraps on the host side and `session-net`'s relay shape wraps on the joiner side
- bin `thaum-session-relay` (`workers/session-relay/bin.rs`): `--port`, `--tls-cert`, `--tls-key`, optional `--plain` (loopback-only dev escape hatch)

## dependency notes
- `workers/session-host/` + `workers/session-client/`: reused unchanged behind the lane
- `serde`/`serde_json`: frames only; session lines are opaque strings
- `rustls` (added at the TLS slice): server + client TLS
- no dependency on `thaum-painter-domain` storage types — the relay never sees records as records

## consumer notes
- `workers/session-net/` (phase-3): `SessionNet::Relay` wires these lanes into the same publish/sync/rejoin/reseed semantics as LAN
- orchestration boot (phase-4): `THAUM_SESSION_RELAY` + code-shaped panel input

## test notes
- `relay_server` inline socket tests: host claim + duplicate-host denial; join + bad-token/no-room/user-collision/room-full denials; joiner→host and host→all/one routing; frame-cap rejection; join-rate rejection; host disconnect closes the room (`room-closed` to all); member disconnect is silent to the room except host-side routing cleanup
- `relay_codes` tests: round-trip, no ambiguous glyphs, wrong-shape rejection
- live TLS test deferred to the deploy phase (certbot-dependent)

## ordering rationale
First of the five phases: everything downstream (session-net lane, orchestration wiring, panel UX, deploy) consumes this boundary's shapes, and nothing else can be tested end-to-end until the relay routes real frames.

## TLS slice — completed 2026-09-08
The "TLS at deploy" deferral landed in-phase (internet-exposed from day one was the settled rule):
- `relay_tls.rs`: `TlsRelayServerAcceptor` (cert/key PEM = certbot output; refuses incomplete pairs at boot) + `connect()` — the one client dial rule. Plain TCP only ever touches loopback or explicit `plain://`; `tls://` forces TLS on loopback (tests); everything else dials TLS with webpki roots, so the deployed LE cert validates like any website. `DEFAULT_RELAY_ADDRESS` = the built-in dev relay consumers' code-joins fall back to.
- Server handshake is driven to completion inside the upgrader, with a deadline; mid-handshake WouldBlock retries. The handshake's final read can carry the first application-data records — those are captured and replayed (`HandshakeBufferedStream`) instead of discarded.
- Client handshake: flush drives ClientHello, bounded by the socket timeout; steady-state uses slice reads so the shared read/write lock always releases.
- `relay_link.rs` bridges refactored onto the shared boxed-stream shape (TLS streams can't `try_clone`); host route/pump loops and the joiner bridge interleave under one lock with slice reads — the same shape the server core uses per connection.
- Tests: in-process TLS end-to-end (rcgen self-signed cert pinned as trust root): TLS dial → host claim → minted code returned, all encrypted.
